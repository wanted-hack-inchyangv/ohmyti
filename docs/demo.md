# 데모 대본 (T-505 → T-907에서 9단계 플로우로 갱신)

이 문서는 PRD 7장의 데모 구간을 실제 화면의 URL·클릭 순서·기대 화면으로 옮겼다. 화면에 나오는 결과와 숫자는 모두
`pnpm demo:seed`가 실제 파이프라인(저장소 확인 → 실행 준비 → 요구사항 검증 → 테스트 실효성 → 리뷰 작성 → 맥락 연결 →
인터뷰 키트)으로 만든 값이다. 화면은 이 저장된 값을 옮기기만 한다. 사전 계산 결과는 어디서나 `저장된 실행 · <시각>`으로
표시한다.

대본은 두 가지다.

- **90초 대본**: 결과를 보여 준다. 결함 샘플 하나를 끝까지 따라간다.
- **3분 확장 대본**: 결과에 이르는 길을 보여 준다. 과제 만들기 → 샘플 이해 → 워크벤치 → 채점 요청 → 리포트.

## 준비

로컬:

```bash
pnpm db:migrate
pnpm demo:seed          # 샘플 과제 승인 확인 → 예시 이력서 업로드 → 샘플 A/B/C/D 제출 → 워커가 전체 파이프라인 실행 → 행 존재 확인
pnpm stack:local        # 웹(4310) + 워커(4320). 데모 중 "새로 실행"까지 보이려면 워커가 떠 있어야 한다
```

배포 환경(Vercel 웹 + Railway 워커): 배포 DB·Blob 스토어를 가리키는 환경변수로

```bash
pnpm demo:seed --env-store --external-worker
```

- `demo:seed`는 샘플마다 새 제출을 만든다. 처음에는 공개 샘플 저장소(`samples/order-api/sample-repos.json`)의 고정 커밋을
  워커가 GitHub에서 수집하고, 그 스냅샷을 `demo/samples/<id>/`에 저장해 두었다가 다음부터는 GitHub 없이 재사용한다.
- 예시 이력서는 두 종류다. 샘플용은 `samples/order-api/demo/resume.txt`(가상 인물 Jordan Lee)를 PDF로 만들어
  `demo/resume.pdf`에 두고, 페르소나용은 `samples/personas/<핸들>/resume.pdf`를 `demo/resumes/<핸들>.pdf`에 올린다.
  채점 요청 폼의 `예시 이력서 사용`(T-902)이 이 두 키만 읽는다.
- LLM(리뷰 작성·맥락 연결·인터뷰 키트·mutation 위치 제안)은 워커 환경에 `DEEP_SEEK_API_KEY`가 있을 때 실제 DeepSeek로 돈다.
  문장은 실행마다 다를 수 있고, 판정·점수는 LLM과 무관하다(G-01).
- 시드가 끝나면 표로 샘플별 평가 ID·점수·실행 기록 수·mutation 실험 수·ai_reviews 행 수를 출력한다. 하나라도 0이면 종료 코드 1이다.
- 서비스는 로그인 없이 공개된다(`APP_ACCESS_MODE=public`). 데모 중 로그인 화면이 나오면 이 환경변수부터 확인한다.

아래 `<C>`는 `/demo`의 `결함 구현 C` 카드가 가리키는 평가 ID다. 이 값은 시드마다 바뀌므로 화면의 링크를 눌러 이동한다.

## 90초 대본

| ------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0~15초  | `/demo`                                                       | ① 홈의 `샘플 체험`으로 들어간다. ② 상단 `채용 과제` 블록과 `추천 체험 순서`를 읽는다                                                                     | 머리에 `채점기 사전 검증 완료` 배지와 안내 문구 "준비된 샘플입니다. 결과와 숫자는 실제 실행에서 생성했습니다". 과제 요약에 명세 발췌·요구사항 15개·총 배점 100점(DB의 승인된 버전에서 읽은 값). 추천 순서는 C → D → A·B → 직접 요청 |
| 15~35초 | `/demo` → `/evaluations/<C>?criterion=R-05`                   | 결함 구현 C 카드의 `이 샘플로 확인할 것` 첫 줄(`R-05 멱등 재전송 …`)을 누른다                                                                            | 카드에 `어떤 구현인가`(구조·제출 테스트 11건·결함 위치)와 공개 저장소·고정 커밋 링크. 링크를 누르면 워크벤치가 R-05를 선택한 채 열리고, 중앙 타임라인의 `stateAfter`에 같은 주문을 두 번 보낸 재고 `2 → 1 → 0`                       |
| 35~55초 | `/evaluations/<C>?criterion=R-05&run=<runId>` → `…&pane=code` | ① 중앙 R-05 실행 기록의 재생을 누른다. ② 아래 `코드` 탭에서 근거 위치를 연다                                                                             | 기대 재고 `1`, 실제 재고 `0`(검사 `p1After.stock`), 요청·응답 순서 강조. 코드 근거는 고정 SHA + 경로 + 라인이며 GitHub 링크는 `blob/<40자 SHA>`만 쓴다. 오른쪽 평가 근거는 `관측`/`추정` 배지로 나뉜다                              |
| 55~70초 | `/evaluations/<C>?criterion=G1&mutation=M-01`                 | 카드의 두 번째 `확인할 것`(또는 왼쪽 `테스트 실효성`의 G1)을 누른다                                                                                      | 이미 있는 재고 부족 거절 로직(R-03)을 지운 변형 M-01에서 하네스는 결함을 잡았지만 제출 테스트 11개는 모두 통과했다(`SURVIVED`). diff와 두 실행 기록이 함께 열린다                                                                    |
| 70~90초 | `/evaluations/<C>/report` → `/evaluations/<C>/interview-kit`  | ① 헤더의 `채용 리포트`를 연다 ② 1절 한눈 요약과 2절 핵심 관측의 근거 링크를 보인다 ③ 6절 면접 안내에서 `인터뷰 키트`로 넘어가 필수 질문 카드 하나를 펼친다 | 리포트 1쪽에 점수 표기 `54~69/100 · 15점 검토 대기`, 영역별 소계, 판정 분포, 검토 대기 항목. 키트는 실패 디브리핑·테스트 설계·이력서 연결 질문을 우선순위와 45·60분 진행안으로 보여 준다. 합격·탈락·등급 표현은 어디에도 없다      |

## 3분 확장 대본

"어떻게 이 결과에 이르렀나"를 보여 주는 대본이다. 90초 대본의 구간을 포함하되 과제 만들기와 직접 채점 요청을 앞뒤로 붙인다.

| 구간      | URL                            | 하는 일                                                                                                                                                                                                                                 |
| --------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0~30초    | `/assignments/new`             | `예시 명세로 채우기`를 누르면 과제 이름·설명·명세 입력란이 주문·재고 API 명세로 찬다. `AI 초안 생성`을 눌러 요구사항·배점 표가 채워지는 것을 보이고, 합계가 100점인지와 `AI 초안 · 미승인` 배지를 짚는다. **저장하지 않고 넘어간다** |
| 30~50초   | `/demo`                        | 과제 요약(명세 발췌·요구사항 수·총 배점)과 추천 체험 순서를 읽는다. 샘플 4종이 "같은 과제를 네 가지 방식으로 제출한 것"임을 말한다                                                                                                      |
| 50~80초   | `/demo` 카드 C·D               | C의 `어떤 구현인가`(멱등성 저장소가 없다)와 D의 `어떤 구현인가`(README·주석·`score.json`·stdout 문구)를 나란히 읽는다. 두 카드의 점수 배지가 같은 값인지 짚는다                                                                          |
| 80~140초  | `/evaluations/<C>?criterion=…` | 90초 대본의 15~70초 구간(R-05 재생 → 코드 근거 → G1·M-01 변이 실험)을 그대로 따른다                                                                                                                                                     |
| 140~165초 | `/submissions/new?sample=C`    | 카드의 `이 샘플로 채점 요청`을 누른다. 저장소 URL·커밋 SHA가 채워져 있고 과제 요약 패널에 요구사항·배점 표와 실행 계약이 보인다. 제출 버튼 위 입력 확인 요약과 `같은 입력으로 저장된 실행 결과 보기` 링크를 짚는다                       |
| 165~180초 | `/demo` 지원자 맥락 예시       | 페르소나 카드(예: 백도현)에서 `채용 리포트`를 연다. 1절 한눈 요약 → 2절 핵심 관측 → 6절 면접 안내 → `인터뷰 키트` 순으로 넘어간다                                                                                                        |

시간이 남으면 `/submissions/new?persona=dohyun`에서 `예시 이력서 사용`을 켜고 실제로 제출해, 상태 화면의 7단계 설명과
저장된 실행에서 잰 참고 소요 시간을 보인다. 실제 채점은 몇 분 걸리므로 `같은 입력으로 저장된 실행 결과 보기` 링크로
기다리지 않고 결과를 볼 수 있다.

## 새로 실행 (선택)

`/demo`의 `이 샘플로 새로 실행`은 저장된 스냅샷으로 새 제출을 만들고 `/demo/runs/<제출 ID>`로 이동한다(GitHub 재수집 없음).

- 워커가 떠 있으면 `대기 중` → `실행 중`을 거쳐 `새 실행 완료`와 `이번 실행 결과 열기` 링크가 나온다. 끝나기 전의 값은 보이지 않는다.
- 실패·미지원으로 끝나거나 워커가 `DEMO_RUN_START_TIMEOUT_MS`(기본 30초) 안에 작업을 가져가지 않고 진행 중인 다른 작업도 없으면
  `새 실행 실패`와 사유가 나온다. 이때 "이번 실행의 결과가 아닙니다"라는 설명과 함께 이전의 `저장된 실행 · <시각>` 링크도 함께 보인다.
  실시간 성공으로 표시하지 않는다.

## 데모 데이터 원칙 대조 (PRD 7장)

| 원칙                                                                   | 화면에서 확인할 곳                                                                                                                       |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 준비된 샘플임을 밝히고 결과와 숫자는 실제 실행에서 생성                | `/demo` 안내 문구, 카드·워크벤치 헤더의 `샘플`·`저장된 실행` 배지. `demo:seed` 출력의 행 수 표                                           |
| 샘플 설명에 판정·점수를 미리 적지 않는다                               | 카드의 `어떤 구현인가`·`이 샘플로 확인할 것`은 볼 대상만 가리킨다. 수치는 카드 아래 `저장된 실행` 블록에만 나온다                        |
| 결함 샘플·올바른 샘플·구조가 다른 올바른 샘플                          | 카드 C(결함)·A(정답)·B(대안 정답). D는 C와 같은 결함에 채점 조작 문구를 넣은 적대적 샘플이며 점수가 C와 같다                             |
| 없는 중복 방지 로직을 다시 제거하는 가짜 mutation 금지                 | C·D의 M-03·M-04가 `NOT_APPLICABLE`(대상 로직 없음). 실험은 R-03·R-04처럼 코드에 있는 로직으로 한다                                       |
| 가짜 진행률·꾸며낸 소요 시간을 쓰지 않는다                             | `/submissions/<id>`의 단계 목록에는 진행률이 없고, 소요 시간은 저장된 실행의 `stage_log`에서 잰 값을 `참고값`이라고 밝혀 보인다 (T-904)  |
| 사전 계산 결과는 `저장된 실행`으로 표시                                | 카드·워크벤치 헤더·새 실행 실패 화면·페르소나 카드의 `저장된 실행 · <시각>`                                                              |
| 새 실행 실패 시 이전 기록을 열 수 있지만 실시간 성공으로 표시하지 않음 | `/demo/runs/<id>`의 `새 실행 실패` 화면                                                                                                  |
