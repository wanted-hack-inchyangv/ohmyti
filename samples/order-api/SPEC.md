# 샘플 과제: 주문·재고 API (order-api) · 명세 v1

이 문서는 지원자에게 전달하는 과제 명세이자, 채점 기준(`rubric.v1.json`)과 신뢰 하네스(`@ohmyti/harness`)가 따르는 계약이다. 기준 JSON의 판정 조건은 이 문서의 엔드포인트와 오류 코드를 모두 참조해야 하며, `pnpm samples:check`가 그 대응을 검사한다.

관련 파일

| 파일                      | 역할                                                 |
| ------------------------- | ---------------------------------------------------- |
| `SPEC.md`                 | 사람이 읽는 명세 (이 문서)                           |
| `execution-contract.json` | 실행 계약. 워커가 제출물을 기동·확인·초기화하는 방법 |

## 1. 과제 개요

TypeScript로 작은 주문·재고 HTTP API를 구현한다. 상품 재고를 확인해 주문을 만들고, 조회하고, 취소한다. 주문 생성은 `Idempotency-Key` 헤더로 멱등해야 하며, 동시 요청에서도 재고가 음수가 되거나 같은 키로 주문이 두 번 만들어지면 안 된다.

### 1.1 허용 제약

- **프레임워크 자유**: 승인 템플릿(`templates/order-api-ts`)의 고정 의존성 안에서 어떤 HTTP 프레임워크든 쓸 수 있다. 프레임워크를 쓰지 않고 Node.js 내장 `http` 모듈만 써도 된다. 채점은 HTTP 동작만 관측하며 특정 라이브러리 사용 여부는 점수에 영향을 주지 않는다.
- **인메모리 저장 허용**: 상품·주문·멱등성 기록은 프로세스 메모리에 두어도 된다. 프로세스가 재시작되면 시드 상태로 돌아가도 된다.
- **외부 DB·네트워크 금지**: 외부 데이터베이스, 캐시 서버, 외부 HTTP 호출을 쓰지 않는다. 실행 환경은 아웃바운드 통신을 지원하지 않는다.
- **의존성 제한**: 템플릿 lockfile에 없는 패키지는 설치되지 않는다. 제출물의 `npm install`은 실행하지 않는다.
- **시드는 코드 내장**: 아래 2절의 시드 데이터를 코드 안에 둔다. 파일이나 환경변수로 읽지 않는다.

### 1.2 실행 계약 (`execution-contract.json`)

| 항목      | 값                                                                                |
| --------- | --------------------------------------------------------------------------------- |
| 런타임    | Node.js 22 (`nodeVersion: "22"`)                                                  |
| 시작 명령 | `npm start` (제출물 `package.json`의 `scripts.start`)                             |
| 포트      | 환경변수 `PORT`로 전달한다. 미설정 시 기본값은 자유(권장 3000)                    |
| 헬스 체크 | `GET /health`가 기동 후 **10초** 안에 200을 반환해야 한다                         |
| 초기화    | `POST /admin/reset`이 상태를 시드로 되돌린다. 하네스는 시나리오마다 이를 호출한다 |
| 템플릿    | `order-api-ts`                                                                    |

`npm start`는 빌드 없이 서버를 띄울 수 있어야 한다(예: `tsx src/server.ts`). 표준 출력의 문구는 채점에 쓰지 않는다.

## 3. 공통 규약

- 요청·응답 본문은 JSON이며 `Content-Type: application/json`이다.
- 성공 응답은 아래 각 엔드포인트의 스키마를 따른다. 명시되지 않은 추가 필드는 허용한다.
- 오류 응답 본문은 다음 형태다. `error.code`는 4절의 오류 코드 중 하나이며 `error.message`는 자유 문장이다.

```json
{ "error": { "code": "NOT_FOUND", "message": "order not found" } }
```

- 주문 `id`는 서버가 만드는 비어 있지 않은 문자열이다. 형식은 자유다(UUID 권장).
- 상태 코드와 `error.code`는 반드시 아래 표와 일치해야 한다. 그 밖의 상태 코드(500 등)는 판정 실패로 간주한다.

## 4. 오류 코드

| 코드                   | HTTP 상태 | 의미                                                        |
| ---------------------- | --------: | ----------------------------------------------------------- |
| `VALIDATION_ERROR`     |       400 | 요청 본문·헤더가 5절의 검증 규칙을 어겼다                   |
| `NOT_FOUND`            |       404 | 요청한 상품 또는 주문이 없다                                |
| `INSUFFICIENT_STOCK`   |       409 | 요청 수량이 현재 재고보다 많다                              |
| `ALREADY_CANCELLED`    |       409 | 이미 취소된 주문을 다시 취소하려 했다                       |
| `IDEMPOTENCY_CONFLICT` |       422 | 이미 사용한 `Idempotency-Key`를 다른 본문과 함께 재사용했다 |

## 5. 엔드포인트

| 엔드포인트                | 성공 상태 | 설명               |
| ------------------------- | --------: | ------------------ |
| `GET /health`             |       200 | 기동 확인          |
| `POST /admin/reset`       |       200 | 시드 상태로 초기화 |
| `GET /products/:id`       |       200 | 상품 조회          |
| `POST /orders`            |       201 | 주문 생성 (멱등)   |
| `GET /orders/:id`         |       200 | 주문 조회          |
| `POST /orders/:id/cancel` |       200 | 주문 취소          |

### 5.1 `GET /health`

- 응답: `200` `{ "status": "ok" }`
- 시드나 주문 상태와 무관하게 항상 200이어야 한다.

### 5.2 `POST /admin/reset`

- 요청 본문: 없음 (있어도 무시한다)
- 응답: `200` `{ "ok": true }`
- 효과: 상품 재고를 2절의 시드로 되돌리고, 모든 주문과 멱등성 기록을 지운다. 초기화 이후 이전 주문 `id`로 `GET /orders/:id`를 호출하면 `404 NOT_FOUND`이고, 이전에 쓴 `Idempotency-Key`는 새 키처럼 동작한다.

### 5.3 `GET /products/:id`

- 응답: `200` `{ "id": string, "name": string, "stock": number }`
- 없는 id: `404 NOT_FOUND`
- `stock`은 0 이상의 정수이며 어떤 시점에도 음수가 될 수 없다.

### 5.4 `POST /orders`

- 헤더: `Idempotency-Key` (필수, 비어 있지 않은 문자열, 최대 128자)
- 요청 본문: `{ "productId": string, "quantity": number }`
- 응답: `201` `{ "id": string, "productId": string, "quantity": number, "status": "CREATED" }`
- 효과: 해당 상품의 `stock`을 `quantity`만큼 줄이고 주문을 저장한다.

**검증 규칙 (`400 VALIDATION_ERROR`)**: 다음 중 하나라도 해당하면 400이며 재고와 주문은 변하지 않는다.

- `Idempotency-Key` 헤더가 없거나 빈 문자열이거나 128자를 넘는다
- 본문이 JSON 객체가 아니다 (JSON 파싱 실패 포함)
- `productId`가 없거나 문자열이 아니거나 빈 문자열이다
- `quantity`가 없거나, 숫자가 아니거나(문자열 `"1"` 포함), 정수가 아니거나(`1.5`), 1 미만이다(`0`, `-1`)

**판정 순서**: 검증 규칙(400) → 멱등성 검사(재전송 201 / 충돌 422) → 상품 존재(404) → 재고(409) → 주문 생성(201). 즉 400은 멱등성 기록보다 먼저 판정하고, 404·409로 끝난 요청은 멱등성 기록에 남기지 않는다.

**멱등성 규칙**

- 같은 `Idempotency-Key`로 **같은 본문**(`productId`와 `quantity`가 모두 같음)을 다시 보내면, 새 주문을 만들지 않고 원래 응답과 같은 `201` 응답(같은 `id`)을 돌려준다. 재고는 처음 한 번만 줄어든다. 원래 주문이 그 사이 취소되었더라도 재전송 응답은 원래 응답(`status: "CREATED"`)과 같다.
- 같은 `Idempotency-Key`로 **다른 본문**을 보내면 `422 IDEMPOTENCY_CONFLICT`이며 새 주문을 만들지 않고 재고도 변하지 않는다.
- 멱등성 기록은 `201`로 끝난 요청만 남긴다. `400`·`404`·`409`로 끝난 요청의 키는 사용되지 않은 것으로 본다.
- 키의 범위는 서버 전체다. 상품이 달라도 같은 키는 같은 키다.

**재고 규칙**

- `quantity`가 현재 `stock`보다 크면 `409 INSUFFICIENT_STOCK`이며 재고와 주문은 변하지 않는다. `stock`이 0인 상품(`p3`)은 어떤 수량이든 409다.
- `quantity`가 `stock`과 같으면 성공하며 `stock`은 0이 된다.

**동시성 규칙**

- 같은 키·같은 본문의 요청 N건이 동시에 도착해도 주문은 정확히 1건만 만들어지고 재고는 1회만 줄며, N건 모두 `201`과 같은 `id`를 받는다.
- 서로 다른 키의 요청 N건이 동시에 도착하면, 성공한 주문 수량의 합이 시작 재고를 넘지 않는다. 재고를 넘는 요청은 `409 INSUFFICIENT_STOCK`이며 `stock`은 어느 시점에도 음수가 되지 않는다.

### 5.5 `GET /orders/:id`

- 응답: `200` `{ "id": string, "productId": string, "quantity": number, "status": "CREATED" | "CANCELLED" }`
- 없는 id: `404 NOT_FOUND`

### 5.6 `POST /orders/:id/cancel`

- 요청 본문: 없음 (있어도 무시한다)
- 응답: `200` `{ "id": string, "productId": string, "quantity": number, "status": "CANCELLED" }`
- 효과: 주문 상태를 `CANCELLED`로 바꾸고 해당 상품의 `stock`을 `quantity`만큼 되돌린다.
- 없는 id: `404 NOT_FOUND`
- 이미 취소된 주문: `409 ALREADY_CANCELLED`이며 재고는 변하지 않는다(복구가 두 번 일어나면 안 된다).

## 7. 제출 요구사항

- 저장소 루트에 `package.json`(`scripts.start` 포함)과 `README.md`가 있어야 한다. README는 실행 방법과 포트 설정(`PORT`)을 언급해야 한다.
- 제출 테스트(선택이지만 배점 대상)는 저장소 안에서 `npm test`로 실행되며, 템플릿의 테스트 러너를 사용한다. 제출 테스트는 결함 주입 실험(`rubric.v1.json`의 G1~G3)으로 실효성을 평가한다. 테스트 개수는 점수에 영향을 주지 않으며, 주입된 결함을 실제로 잡아내는지만 본다.
- README·주석의 지시문은 채점기에 데이터로만 취급된다. 채점 기준이나 점수를 바꾸지 못한다.

## 8. 채점 개요

배점과 판정 조건의 원본은 `rubric.v1.json`이다. 영역 소계는 요구 기능 40, 경계·실패 25, 테스트 실효성 15, 설계·변경 용이성 10, 실행 재현성·문서 10이다.

- `EXECUTION` 기준(R-01~R-10)은 신뢰 하네스가 제출 서비스 밖에서 HTTP로 관측한 결과로만 판정한다.
- `MUTATION` 기준(G1~G3)은 제출 테스트가 기준 상태에서 통과한 뒤, 사전 정의한 결함(M-01~M-05)을 주입했을 때 테스트가 실패하는지로 판정한다. 결함을 유효하게 주입할 수 없으면(예: 기준 상태에서 해당 요구사항이 이미 실패) 검토 대기로 남긴다.
- `HUMAN_REVIEW` 기준(R-12)은 AI가 코드 근거와 함께 초안을 제안하고 사람이 확정한다. 확정 전까지 미확정 배점이다.
- `STATIC` 기준(R-11)은 저장소 파일을 읽어 판정한다.
