- G1, G2, G3 (테스트 실효성): 모두 실패(0점) 기대. 제출 테스트는 기준 상태에서 전부 통과하지만 단언이 허술해 M-01 ~ M-05를 적용해도 테스트가 실패하지 않는다(아래 "구현 특징과 결함" 참고).

## 구현 특징과 결함

R-01 ~ R-10은 모두 통과하도록 만들었으므로 여기서는 코드 품질 문제와 테스트 실효성 문제를 항목별로 적는다.

- **단일 파일에 모든 책임 집중**: `src/index.ts` 전체(1 ~ 344줄)에 라우팅, 입력 검증, 도메인 로직, 오류 응답 생성이 뒤섞여 있다. 상태는 모듈 최상위의 `let products`, `let orders`, `let idemStore`(14 ~ 24줄)에 직접 둔다. HTTP 요청·응답 객체와 도메인 판정이 분리되어 있지 않다.
- **`any` 남발과 `strict` 끔**: `tsconfig.json`에서 `strict: false`로 꺼 두었고, `product_id`·`qty`·`existing`·`product`·`data2` 등 거의 모든 지역 변수가 `any`다(90 ~ 91줄, 106줄, 122줄, 190줄, 296줄). `req.header(...) as any`(76줄)처럼 필요한 곳에서 타입 오류를 그냥 넘긴다.
- **검증·오류 응답 코드 복붙**: `POST /orders` 핸들러(98 ~ 234줄) 안에서 `res.status(...).json({ error: { code: ... } })` 형태가 상수화 없이 10곳 넘게 반복된다(105 ~ 158줄). 상태 코드와 오류 코드 문자열이 각 지점에 직접 적혀 있다.
- **깊게 중첩된 if/else**: `productId` 검증(129 ~ 142줄)이 `if (...) { ... } else { if (...) { ... } else { if (...) { ... } } }` 형태로 불필요하게 중첩되어 있다.
- **변수명과 표기법 혼용**: `product_id`(126줄, snake_case)와 API 필드명 `productId`(camelCase)가 같은 함수 안에서 혼용된다. `tmp`(201줄), `data2`(296줄), `flag`(283줄) 같은 의미 없는 변수명을 쓴다.
- **남은 디버그 흔적**: 23줄에 `// TODO 나중에 정리: 이거 계속 쌓이기만 하는데...` 주석이 있고, 67줄과 228줄에 `console.log`가 그대로 남아 있다.
- **멱등성 저장소가 문자열 비교뿐**: `idemStore`(24줄)는 인터페이스 없이 배열이며, 같은 요청인지 판정은 `JSON.stringify(req.body)` 문자열 동등 비교(165, 177줄)로만 한다. 기록은 `POST /admin/reset` 전까지 만료되지 않고 계속 쌓인다.
- **폴링 기반 전역 락**: `lockit`/`unlockit`(25 ~ 39줄)이 `while (locked) await sleep(1)`로 모든 쓰기 요청(주문 생성·취소·초기화)을 직렬화한다. 조악하지만 JS 이벤트 루프의 동기 실행 특성상 조건 검사와 락 설정 사이에 다른 요청이 끼어들 수 없어 R-07·R-08은 안정적으로 통과한다.

### 변이 주입 결과 (M-01 ~ M-05)

각 변이를 `src/index.ts`에 직접 적용한 뒤 `npm test`를 실행하고, 결과를 기록한 다음 원래 코드로 되돌렸다. 다섯 변이 모두 테스트가 그대로 통과해 생존했다.
